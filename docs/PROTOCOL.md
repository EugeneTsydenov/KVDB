# Протокол KVDB

Протокол описывает обмен данными между клиентом и сервером KVDB по UDP. Одна UDP-датаграмма содержит одно сообщение Protocol Buffers (Protobuf) - запрос, ответ или подтверждение получения (ACK).

Сообщения сериализуются с помощью Protobuf. UDP используется как транспорт, а надёжность доставки реализуется на уровне приложения.

## 1. Общие правила

Все сообщения описываются в `api/proto/kvdb.proto` с использованием `proto3`. Go-код для сериализации и десериализации генерируется из этой схемы.

В протоколе используются следующие типы:

- `uint32`, `uint64` - беззнаковые целые числа;
- `sint64` - знаковое целое число с ZigZag-кодированием;
- `bytes` - произвольная последовательность байтов;
- `string` - строка в UTF-8;
- `repeated` - список значений;
- `enum` - набор именованных числовых значений;
- `oneof` - одно из нескольких взаимоисключающих полей сообщения.

Все числовые значения кодируются по правилам Protobuf. Для полей с типами `uint32`, `uint64` и `sint64` не используется фиксированное расположение в пакете или собственное big-endian-кодирование.

Один сериализованный `Packet` целиком передаётся в одной UDP-датаграмме. Отдельного фиксированного `Header` и поля `payload_len` нет. Размер определяется длиной полученного или сформированного набора байтов.

Protobuf проверяет корректность бинарного представления, но не проверяет правила команд KVDB. После десериализации сервер отдельно проверяет версию, тип сообщения, идентификаторы, аргументы и установленные ограничения.

## 2. Ограничения

| Параметр | Значение |
|---|---:|
| `MaxPacketSize` - максимальный размер сериализованного `Packet` | 1400 байт |
| `MaxKeyLen` - максимальная длина ключа | 256 байт |
| `MaxValueLen` - максимальная длина значения | 1024 байта |
| `MaxPatternLen` - максимальная длина регулярного выражения | 256 байт |
| `MaxErrorLen` - максимальная длина сообщения об ошибке | 256 байт |
| `MaxTTLMs` - максимальный TTL | 9223372036854 мс |

Ограничение `MaxPacketSize` относится ко всему Protobuf-сообщению, включая `version`, идентификаторы, `operation`, тип сообщения и данные команды. Отдельного постоянного `MaxPayloadSize` нет: служебные поля Protobuf имеют переменный размер.

Перед отправкой клиент и сервер сериализуют сообщение и проверяют, что `len(data) <= MaxPacketSize`. Если запрос больше допустимого размера, клиент не отправляет его. Если успешный ответ не помещается в пакет, сервер формирует короткий ответ со статусом `TOO_LARGE`, сохраняя идентификаторы исходного запроса.

При получении UDP-сервер использует буфер размером не меньше `MaxPacketSize + 1` байт и отбрасывает слишком большие датаграммы до вызова `proto.Unmarshal`. Усечённый пакет нельзя передавать декодеру как полноценное сообщение.

`MaxTTLMs` ограничивает значение, которое можно безопасно перевести в наносекунды и хранить в `int64`. Превышение лимита приводит к `INVALID_ARGUMENT`.

Лимит 1400 байт выбран для снижения риска IP-фрагментации, но сам по себе не гарантирует её отсутствие на любом сетевом маршруте.

## 3. Структура пакета

Корневое сообщение `Packet` одинаково для запросов, ответов и ACK. Тип сообщения определяется заполненным полем `oneof body`.

| Номер поля | Поле | Тип | Описание |
|---|---|---|---|
| 1 | `version` | `uint32` | Версия протокола, поддерживается значение `1` |
| 2 | `client_id` | `uint64` | Идентификатор клиентской сессии |
| 3 | `request_id` | `uint64` | Идентификатор логического запроса |
| 4 | `sequence` | `uint32` | Порядковый номер запроса в сессии |
| 5 | `op` | `Operation` | Код команды KVDB |
| 10 | `request` | `Request` | Аргументы команды |
| 11 | `response` | `Response` | Результат выполнения |
| 12 | `ack` | `Ack` | Подтверждение принятия запроса |

Поля `request`, `response` и `ack` входят в один `oneof body`. В корректном сообщении должно быть установлено ровно одно из них. Пустое сообщение `Ack` считается установленным, только если присутствует соответствующий вариант `oneof`.

`version = 1` обязателен для всех сообщений. Значения `client_id`, `request_id` и `sequence` должны быть ненулевыми. Сервер копирует `client_id`, `request_id`, `sequence` и `op` из запроса в ACK и итоговый ответ.

### 3.1. Идентификатор клиента

`client_id` создаётся при запуске клиентской сессии как случайное ненулевое 64-битное число. Он позволяет отличать запросы разных клиентов, даже если те используют одинаковый `request_id`.

Идентификатор должен генерироваться криптографически стойким источником случайности, например `crypto/rand` в Go. Вероятность случайного совпадения не равна нулю, поэтому протокол не обещает абсолютную уникальность случайных идентификаторов.

### 3.2. Идентификатор запроса

`request_id` идентифицирует один логический запрос внутри клиентской сессии. Для каждого нового запроса клиент использует новое значение. При повторной отправке `request_id` не меняется.

Сервер использует пару `(client_id, request_id)` как ключ поиска в кэше дедупликации.

### 3.3. Порядковый номер

`sequence` увеличивается на единицу для каждого нового логического запроса в одной клиентской сессии. При Retry номер остаётся исходным. Номер не предназначен для упорядочивания выполнения команд на сервере: UDP может доставлять сообщения в другом порядке.

При исчерпании диапазона `uint32` клиент должен создать новую сессию с новым `client_id`, а не повторно использовать старые значения `sequence` в той же сессии.

## 4. Команды

| Код | Команда | Назначение |
|---|---|---|
| `1` | `PING` | Проверка связи |
| `2` | `GET` | Получение значения |
| `3` | `SET` | Запись значения |
| `4` | `SETNX` | Запись, если ключ ещё не существует |
| `5` | `DEL` | Удаление ключа |
| `6` | `TTL` | Получение оставшегося TTL |
| `7` | `EXPIRE` | Изменение TTL существующего ключа |
| `8` | `KEYS` | Поиск ключей по регулярному выражению |

Значение `OP_UNSPECIFIED = 0` не является командой. Неизвестные числовые значения `Operation` сервер обрабатывает как `UNKNOWN_OPCODE`, если может сформировать корректный ответ.

Во всех командах просроченный ключ считается отсутствующим.

## 5. Формат запроса и ответа

`Packet.request` содержит общую структуру `Request`. Для каждой команды используются только необходимые поля. Неиспользуемые поля должны иметь нулевые значения и не должны передавать дополнительную семантику.

| Поле `Request` | Тип | Назначение |
|---|---|---|
| `key` | `bytes` | Ключ для GET, SET, SETNX, DEL, TTL, EXPIRE |
| `value` | `bytes` | Значение для SET и SETNX |
| `ttl_ms` | `uint64` | TTL для SET, SETNX и EXPIRE |
| `pattern` | `string` | Регулярное выражение для KEYS |
| `cursor` | `uint64` | Зарезервировано для пагинации KEYS |
| `limit` | `uint32` | Зарезервировано для пагинации KEYS |

`Packet.response` содержит структуру `Response`:

| Поле `Response` | Тип | Назначение |
|---|---|---|
| `status` | `Status` | Результат выполнения команды |
| `value` | `bytes` | Значение GET |
| `ttl_ms` | `sint64` | Оставшийся TTL |
| `deleted` | `uint64` | Количество удалённых ключей |
| `keys` | `repeated bytes` | Список ключей KEYS |
| `message` | `string` | Описание ошибки |

### 5.1. PING

Запрос не содержит аргументов. Успешный ответ имеет статус `OK` без дополнительных данных.

### 5.2. GET

| Сообщение | Поля |
|---|---|
| Запрос | `key` |
| Ответ `OK` | `value` |
| Ответ `NOT_FOUND` | Дополнительных данных нет |

Если ключ существует и не истёк, сервер возвращает его значение. Пустое значение допустимо. Если ключ отсутствует или истёк, возвращается `NOT_FOUND`.

### 5.3. SET

| Сообщение | Поля |
|---|---|
| Запрос | `key`, `value`, `ttl_ms` |
| Ответ `OK` | Дополнительных данных нет |

Команда записывает значение. Если ключ существует, его значение и TTL заменяются.

Значения `ttl_ms`:

- `0` - ключ без ограничения по времени;
- от `1` до `MaxTTLMs` - срок жизни в миллисекундах;
- больше `MaxTTLMs` - `INVALID_ARGUMENT`.

### 5.4. SETNX

Формат запроса совпадает с `SET`.

| Статус | Результат |
|---|---|
| `OK` | Новый ключ создан |
| `NOT_SET` | Ключ уже существует и не был перезаписан |

Просроченный ключ считается отсутствующим. Правила `ttl_ms` совпадают с `SET`.

### 5.5. DEL

| Сообщение | Поля |
|---|---|
| Запрос | `key` |
| Ответ `OK` | `deleted` |

`deleted = 1`, если ключ удалён, и `deleted = 0`, если его не было или он истёк. Оба результата имеют статус `OK`.

### 5.6. TTL

| Сообщение | Поля |
|---|---|
| Запрос | `key` |
| Ответ `OK` | `ttl_ms: sint64` |
| Ответ `NOT_FOUND` | Дополнительных данных нет |

Значения `ttl_ms`:

- `-1` - ключ существует без TTL;
- `0` - положительное оставшееся время меньше миллисекунды;
- положительное число - оставшееся время жизни в миллисекундах.

Оставшийся TTL передаётся в целых миллисекундах. Для положительного остатка меньше 1 мс допускается значение `0`. Если ключ отсутствует или истёк, сервер возвращает `NOT_FOUND`.

### 5.7. EXPIRE

| Сообщение | Поля |
|---|---|
| Запрос | `key`, `ttl_ms` |
| Ответ `OK` | Дополнительных данных нет |
| Ответ `NOT_FOUND` | Дополнительных данных нет |

Команда устанавливает новый TTL существующего ключа. Значение ключа не меняется. TTL должен находиться в диапазоне от `1` до `MaxTTLMs`; иначе возвращается `INVALID_ARGUMENT`.

### 5.8. KEYS

| Сообщение | Поля |
|---|---|
| Запрос | `pattern`, `cursor = 0`, `limit = 0` |
| Ответ `OK` | `keys` |

Поиск выполняется регулярным выражением RE2. Паттерн сопоставляется с любой частью ключа; для полного совпадения используются `^` и `$`. Пустой паттерн подходит всем ключам. Просроченные ключи не возвращаются.

Результат содержит ключи в лексикографическом порядке. Если совпадений нет, передаётся пустой список `keys` со статусом `OK`.

Пагинация пока не поддерживается. Поля `cursor` и `limit` в запросе должны быть нулевыми. Ненулевые значения приводят к `INVALID_ARGUMENT`. Если список не помещается в UDP-пакет, сервер отвечает `TOO_LARGE` вместо частичного результата.

Некорректное регулярное выражение приводит к `INVALID_ARGUMENT`.

## 6. Статусы ответов

| Код | Статус | Когда используется |
|---|---|---|
| `0` | `OK` | Команда выполнена успешно |
| `1` | `NOT_FOUND` | Ключ отсутствует или истёк |
| `2` | `NOT_SET` | SETNX не изменил существующий ключ |
| `16` | `BAD_REQUEST` | Некорректный формат или поля сообщения |
| `17` | `UNKNOWN_OPCODE` | Неизвестная команда |
| `18` | `UNSUPPORTED_VERSION` | Неподдерживаемая версия протокола |
| `19` | `TOO_LARGE` | Превышен лимит поля или пакета |
| `20` | `INVALID_ARGUMENT` | Недопустимое значение аргумента |
| `21` | `REQUEST_CONFLICT` | Тот же идентификатор запроса использован для другой операции |
| `22` | `SERVER_BUSY` | Сервер не может безопасно принять запрос, например заполнен кэш дедупликации |
| `127` | `INTERNAL_ERROR` | Внутренняя ошибка сервера |

Статусы `REQUEST_CONFLICT` и `SERVER_BUSY` используются механизмами надёжности. Коды операций и статусов задаются этой спецификацией.

`NOT_FOUND` допускается только для GET, TTL и EXPIRE; `NOT_SET` - только для SETNX. При ошибке сервер заполняет `message`, длина которого не превышает 256 байт. Тип ошибки определяется по `status`, а не по тексту сообщения.

Коды ошибок не являются основанием автоматически повторять запрос: полученный финальный `Response` завершает логическую операцию. Повторный запрос создаётся только по правилам Retry.

## 7. ACK и итоговый ответ

ACK - отдельный вариант `Packet.body`, подтверждающий, что корректный запрос принят сервером и зарегистрирован для обработки. ACK не подтверждает успешное выполнение команды или сохранность данных после сбоя.

Сервер вправе отправить итоговый `Response` без предварительного ACK. Для коротких команд это предпочтительный вариант, поскольку отдельный ACK увеличивает сетевой трафик.

Если сервер отправляет ACK, он должен передать исходные `client_id`, `request_id`, `sequence` и `op`. Payload сообщения `Ack` пустой.

Клиент применяет следующие правила:

1. ACK с чужими идентификаторами не относится к текущему запросу.
2. Получение ACK не завершает `Do` и не считается успешным выполнением команды.
3. Получение корректного итогового `Response` завершает ожидание независимо от того, приходил ли ACK.
4. Отсутствие ACK само по себе не означает, что запрос потерян.
5. Если получен только ACK, клиент продолжает ожидание финального ответа в пределах общего deadline и может повторить запрос по Retry Policy.
6. Поздние ACK и ответы от предыдущих запросов не должны ошибочно завершать новый запрос.

## 8. Retry и таймауты

UDP не гарантирует доставку пакетов. Если клиент не получил итоговый ответ, он может повторить отправку исходного запроса.

Начальная политика клиента:

| Параметр | Значение |
|---|---:|
| `MaxAttempts` - максимальное число отправок, включая первую | 3 |
| `AttemptTimeout` - время ожидания на одну попытку | 200 мс |
| `TotalTimeout` - общий предел выполнения запроса | 1 секунда |

Эти параметры могут быть настраиваемыми. Общий deadline ограничивает суммарное ожидание, включая все попытки и обработку ACK.

При Retry клиент повторно отправляет **тот же сериализованный набор байтов**. `client_id`, `request_id`, `sequence`, `op` и тело запроса не меняются. Новый RequestID для повторной попытки создавать нельзя.

Получение любого корректного финального Response, в том числе `NOT_FOUND` или `INVALID_ARGUMENT`, прекращает повторы. При исчерпании попыток или общего deadline клиент возвращает ошибку. Такая ошибка не гарантирует, что сервер не выполнил команду.

Для запросов одного `Client` допускается последовательная отправка с синхронизацией доступа к сокету. При последующей параллельной обработке ответы должны сопоставляться с ожидающими запросами по идентификаторам.

## 9. Детекция дубликатов

Для предотвращения повторного исполнения команд сервер использует Deduplication Cache.

Ключ кэша - пара `(client_id, request_id)`. Запись также содержит отпечаток содержимого запроса, его состояние и при успешном завершении - готовые сериализованные байты итогового ответа.

| Состояние | Описание |
|---|---|
| `IN_FLIGHT` | Запрос принят, но окончательный результат ещё не сохранён |
| `COMPLETED` | Запрос обработан, итоговый ответ сохранён |

Поведение сервера:

1. Для нового запроса атомарно создаётся запись `IN_FLIGHT` до выполнения команды.
2. После обработки сохраняется финальный Response, а запись переходит в `COMPLETED`.
3. При точном повторе `COMPLETED` сервер возвращает сохранённый Response, не вызывая команду повторно.
4. При повторе `IN_FLIGHT` сервер не запускает команду второй раз. Он может повторить ACK или дождаться готового ответа согласно реализации.
5. При одинаковых `(client_id, request_id)` и различающемся содержимом запроса сервер отвечает `REQUEST_CONFLICT`, не выполняя новый запрос.

Для сравнения содержимого можно использовать криптографический отпечаток исходного логического запроса. Необходимо сравнивать одни и те же логические поля независимо от попытки доставки; ACK и финальный ответ не входят в отпечаток запроса.

### Ограничения кэша

| Параметр | Начальное значение |
|---|---:|
| Время хранения завершённого запроса (`Retention`) | 60 секунд |
| Максимальное число записей | 100000 |

Запись `COMPLETED` хранится не меньше заданного Retention с момента завершения. Запись `IN_FLIGHT` не должна удаляться по обычному сроку хранения завершённых записей, пока операция выполняется.

При заполнении кэша сервер может удалить записи с истёкшим сроком хранения. Если безопасно освободить место невозможно, новый запрос не исполняется и сервер возвращает `SERVER_BUSY`.

После перезапуска сервера кэш теряется. По истечении Retention повторный запрос тоже может быть исполнен заново. Поэтому протокол гарантирует подавление повторного исполнения только в пределах жизни сервера и действующего окна дедупликации. Глобальная гарантия `exactly once` не предоставляется.

## 10. Обработка некорректных пакетов

| Ситуация | Действие |
|---|---|
| Датаграмма больше 1400 байт | Отбросить без декодирования и ответа |
| Пустая датаграмма или ошибка `proto.Unmarshal` | Отбросить без ответа |
| Нет варианта `oneof body` | Отбросить без ответа |
| Получен `response` или `ack` вместо клиентского запроса | Отбросить без выполнения команды |
| Неподдерживаемая `version` | Вернуть `UNSUPPORTED_VERSION`, если можно безопасно прочитать идентификаторы и сформировать ответ; иначе отбросить |
| Неизвестный `op` | Вернуть `UNKNOWN_OPCODE`, если envelope корректен |
| Нулевой `client_id`, `request_id` или `sequence` | Отбросить без ответа |
| Неверные поля команды | Вернуть `BAD_REQUEST` или `INVALID_ARGUMENT` |
| Превышение длины `key`, `value`, `pattern` | Вернуть `TOO_LARGE` |
| Несовпадение идентификатора уже известного запроса и его содержимого | Вернуть `REQUEST_CONFLICT` |
| Слишком большой успешный ответ | Вернуть короткий `TOO_LARGE` |

Неизвестные поля Protobuf могут сохраняться или игнорироваться декодером согласно правилам Protobuf, но неизвестный тип сообщения, неподдерживаемая версия и недопустимые значения известных полей не должны приводить к выполнению команды.

Каждый сформированный ответ должен помещаться в `MaxPacketSize` и сохранять идентификаторы соответствующего запроса. Ошибочный пакет не должен вызывать panic или нарушать обработку следующих датаграмм.

## 11. Расширение протокола

Протокол описывает взаимодействие клиента с KVDB. Распределение ключей между узлами, репликация, обмен состоянием кластера и выбор нового ведущего узла относятся к внутренней логике сервера и не требуют дополнительных полей в текущих клиентских сообщениях.

При расширении Protobuf-схемы новые поля получают новые номера. Номера и имена удалённых полей следует помечать как `reserved` и не использовать повторно. Существующие поля не должны менять смысл. Неизвестные поля не должны приводить к выполнению неподдерживаемой команды.

Поля `cursor` и `limit` предусмотрены для будущей пагинации `KEYS`, но сейчас обязаны быть равны нулю. Если позднее потребуется возвращать страницы результатов, формат `Response` можно расширить полем `next_cursor` без изменения существующих номеров полей.

Возможные команды управления кластером, перенаправления запросов и внутренние сообщения репликации будут описаны отдельно, когда появится соответствующая функциональность. Заранее добавлять их в `Packet` не требуется.

## 12. Примеры сообщений

Примеры ниже показывают логическое содержимое Protobuf-сообщений до сериализации. Это не JSON wire-формат и не точное представление передаваемых байтов.

### PING: проверка связи

```text
Packet {
  version: 1
  client_id: 100
  request_id: 1
  sequence: 1
  op: OP_PING
  request: {}
}
```

Сервер может сразу вернуть итоговый ответ:

```text
Packet {
  version: 1
  client_id: 100
  request_id: 1
  sequence: 1
  op: OP_PING
  response: { status: STATUS_OK }
}
```

### GET: получение значения `user:1`

```text
Packet {
  version: 1
  client_id: 100
  request_id: 2
  sequence: 2
  op: OP_GET
  request: { key: "user:1" }
}
```

Успешный ответ со значением `Alice`:

```text
Packet {
  version: 1
  client_id: 100
  request_id: 2
  sequence: 2
  op: OP_GET
  response: {
    status: STATUS_OK
    value: "Alice"
  }
}
```

### SET: запись значения с TTL

```text
Packet {
  version: 1
  client_id: 100
  request_id: 3
  sequence: 3
  op: OP_SET
  request: {
    key: "session"
    value: "abc"
    ttl_ms: 5000
  }
}
```

Если сервер отправляет ACK, он повторяет идентификаторы запроса:

```text
Packet {
  version: 1
  client_id: 100
  request_id: 3
  sequence: 3
  op: OP_SET
  ack: {}
}
```

Итоговый результат передаётся отдельно:

```text
Packet {
  version: 1
  client_id: 100
  request_id: 3
  sequence: 3
  op: OP_SET
  response: { status: STATUS_OK }
}
```

### Повторная отправка SET

Если итоговый ответ потерялся, клиент повторно отправляет исходный `Packet` с теми же `client_id = 100`, `request_id = 3` и `sequence = 3`.

Если запрос уже имеет состояние `COMPLETED`, сервер отправляет сохранённый ответ и не выполняет `SET` повторно.

### KEYS: поиск по паттерну `user:.*`

```text
Packet {
  version: 1
  client_id: 100
  request_id: 4
  sequence: 4
  op: OP_KEYS
  request: {
    pattern: "user:.*"
    cursor: 0
    limit: 0
  }
}
```

При наличии совпадений:

```text
Packet {
  version: 1
  client_id: 100
  request_id: 4
  sequence: 4
  op: OP_KEYS
  response: {
    status: STATUS_OK
    keys: ["user:1", "user:2"]
  }
}
```

Если сериализованный список не помещается в 1400 байт, вместо него возвращается `STATUS_TOO_LARGE` с коротким описанием ошибки.
