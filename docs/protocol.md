# Бинарный протокол

Протокол используется для обмена данными между клиентом и сервером по UDP. Каждый пакет содержит одно сообщение: запрос или ответ на него.

## 1. Общие правила

Все многобайтные числа передаются в формате big-endian.

Используются следующие типы данных:

- `u8`, `u16`, `u64` — беззнаковые целые числа;
- `i64` — знаковое целое число;
- `bytes` — длина данных (`u16`), за которой следуют сами данные;
- `string` — строка в UTF-8, формат такой же, как у `bytes`.

При чтении данных необходимо проверять, хватает ли оставшихся байтов для текущего поля. Если данных недостаточно, декодер должен вернуть ошибку, а не завершаться с паникой.

## 2. Ограничения

| Параметр                                               | Значение   |
| ------------------------------------------------------ | ---------- |
| Максимальный размер пакета (`MaxPacketSize`)           | 1400 байт  |
| Размер заголовка (`HeaderSize`)                        | 16 байт    |
| Максимальный размер payload (`MaxPayloadSize`)         | 1384 байта |
| Максимальная длина ключа (`MaxKeyLen`)                 | 256 байт   |
| Максимальная длина значения (`MaxValueLen`)            | 1024 байта |
| Максимальная длина regex (`MaxPatternLen`)             | 256 байт   |
| Максимальная длина сообщения об ошибке (`MaxErrorLen`) | 256 байт   |

Например, запрос `SET` с ключом длиной 256 байт, значением длиной 1024 байта и полем TTL занимает 1292 байта payload. Такой пакет укладывается в установленный лимит.

## 3. Формат заголовка

Заголовок занимает 16 байт и используется как в запросах, так и в ответах.

| Смещение | Размер | Поле          | Описание                        |
| -------- | ------ | ------------- | ------------------------------- |
| 0        | 2      | `magic`       | Константа `0x4B56`              |
| 2        | 1      | `version`     | Версия протокола, сейчас `0x01` |
| 3        | 1      | `opcode`      | Код команды                     |
| 4        | 1      | `status`      | Код результата                  |
| 5        | 1      | `flags`       | Флаги сообщения                 |
| 6        | 2      | `payload_len` | Размер payload в байтах         |
| 8        | 8      | `request_id`  | Идентификатор запроса           |

Поле `magic` всегда равно `0x4B56`. Версия текущего протокола — `0x01`.

В поле `flags` используется только младший бит (`0x01`): он равен `0` для запроса и `1` для ответа. Остальные биты должны быть нулевыми.

В запросе поле `status` всегда равно `0x00`. Сервер возвращает тот же `request_id`, который получил от клиента. Это позволяет сопоставить ответ с исходным запросом.

После заголовка идут данные payload. Их размер должен совпадать со значением `payload_len`.

### Проверка входящего пакета

При разборе заголовка выполняются следующие проверки:

1. Размер датаграммы должен быть не меньше 16 и не больше 1400 байт.
2. Значение `magic` должно быть равно `0x4B56`.
3. Версия должна поддерживаться сервером.
4. `payload_len` должен совпадать с фактическим размером данных после заголовка.
5. В `flags` не должно быть установлено неизвестных битов.
6. Для запроса `flags` должен быть равен `0`, а `status` — `0x00`. Для ответа младший бит `flags` должен быть равен `1`.

После проверки заголовка сервер разбирает payload в соответствии с командой. Если после чтения всех полей остаются лишние байты, пакет считается некорректным.

## 4. Команды

Для каждой команды используется свой код `opcode`.

| Код    | Команда  | Назначение                                     |
| ------ | -------- | ---------------------------------------------- |
| `0x01` | `PING`   | Проверить доступность сервера                  |
| `0x02` | `GET`    | Получить значение по ключу                     |
| `0x03` | `SET`    | Записать значение                              |
| `0x04` | `SETNX`  | Записать значение, если ключ ещё не существует |
| `0x05` | `DEL`    | Удалить ключ                                   |
| `0x06` | `TTL`    | Узнать оставшееся время жизни ключа            |
| `0x07` | `EXPIRE` | Установить время жизни существующего ключа     |
| `0x08` | `KEYS`   | Найти ключи по регулярному выражению           |

В ответе сервер использует тот же `opcode` и `request_id`, что и в запросе. Если команда неизвестна, сервер возвращает `UNKNOWN_OPCODE`.

## 5. Формат команд

### PING

Запрос и успешный ответ не содержат payload. Команда нужна для проверки связи с сервером.

### GET

| Направление       | Payload        |
| ----------------- | -------------- |
| Запрос            | `key: bytes`   |
| Ответ `OK`        | `value: bytes` |
| Ответ `NOT_FOUND` | Пустой         |

Если ключ существует, сервер возвращает его значение. Если ключа нет или срок его жизни истёк, возвращается `NOT_FOUND`.

### SET

| Направление | Payload                                     |
| ----------- | ------------------------------------------- |
| Запрос      | `key: bytes`, `value: bytes`, `ttl_ms: u64` |
| Ответ `OK`  | Пустой                                      |

Команда записывает значение по указанному ключу. Поле `ttl_ms` задаёт время жизни в миллисекундах. Если оно равно `0`, ключ сохраняется без ограничения по времени.

### SETNX

Формат запроса такой же, как у `SET`.

| Ответ     | Значение                            |
| --------- | ----------------------------------- |
| `OK`      | Ключ создан, payload пустой         |
| `NOT_SET` | Ключ уже существует, payload пустой |

Команда не перезаписывает существующий ключ.

### DEL

| Направление       | Payload      |
| ----------------- | ------------ |
| Запрос            | `key: bytes` |
| Ответ `OK`        | Пустой       |
| Ответ `NOT_FOUND` | Пустой       |

`OK` возвращается, если ключ удалось удалить. Если ключ отсутствует, сервер отвечает `NOT_FOUND`.

### TTL

| Направление       | Payload       |
| ----------------- | ------------- |
| Запрос            | `key: bytes`  |
| Ответ `OK`        | `ttl_ms: i64` |
| Ответ `NOT_FOUND` | Пустой        |

Поле `ttl_ms` содержит оставшееся время жизни ключа в миллисекундах. Значение `-1` означает, что ключ не имеет срока жизни.

Если ключ отсутствует или уже истёк, сервер возвращает `NOT_FOUND`.

### EXPIRE

| Направление       | Payload                     |
| ----------------- | --------------------------- |
| Запрос            | `key: bytes`, `ttl_ms: u64` |
| Ответ `OK`        | Пустой                      |
| Ответ `NOT_FOUND` | Пустой                      |

Команда устанавливает новый срок жизни существующего ключа. Значение `ttl_ms` должно быть больше нуля. Если передано `0`, сервер возвращает `INVALID_ARGUMENT`.

Если ключа нет, возвращается `NOT_FOUND`.

### KEYS

| Направление | Payload                                                             |
| ----------- | ------------------------------------------------------------------- |
| Запрос      | `pattern: bytes`, `cursor: u64`, `limit: u16`                       |
| Ответ `OK`  | `next_cursor: u64`, `count: u16`, затем `count` ключей типа `bytes` |

Команда возвращает ключи, которые соответствуют регулярному выражению RE2.

Паттерн проверяется на совпадение с любой частью ключа. Чтобы проверить ключ целиком, нужно использовать `^` и `$`. Пустой паттерн соответствует всем ключам.

Поскольку все ключи могут не поместиться в один UDP-пакет, результат возвращается частями. Для первого запроса передаётся `cursor = 0`. Если ключи ещё остались, сервер возвращает ненулевой `next_cursor`. Его нужно передать в следующем запросе. Когда обход завершён, `next_cursor` равен `0`.

Курсор является внутренним значением сервера. Клиент не должен самостоятельно вычислять или изменять его.

Поле `limit` задаёт максимальное количество ключей в ответе. Если оно равно `0`, сервер использует значение по умолчанию. При необходимости сервер уменьшает количество ключей, чтобы ответ не превышал `MaxPayloadSize`.

Если регулярное выражение некорректно, возвращается `INVALID_ARGUMENT`.

## 6. Коды статусов

Сервер указывает результат выполнения команды в поле `status`.

| Код    | Статус                | Описание                                                |
| ------ | --------------------- | ------------------------------------------------------- |
| `0x00` | `OK`                  | Команда выполнена успешно                               |
| `0x01` | `NOT_FOUND`           | Ключ отсутствует или срок его жизни истёк               |
| `0x02` | `NOT_SET`             | `SETNX` не выполнен, поскольку ключ уже существует      |
| `0x10` | `BAD_REQUEST`         | Некорректный payload                                    |
| `0x11` | `UNKNOWN_OPCODE`      | Неизвестная команда                                     |
| `0x12` | `UNSUPPORTED_VERSION` | Неподдерживаемая версия протокола                       |
| `0x13` | `TOO_LARGE`           | Превышен допустимый размер ключа, значения или паттерна |
| `0x14` | `INVALID_ARGUMENT`    | Некорректный аргумент команды                           |
| `0x7F` | `INTERNAL_ERROR`      | Внутренняя ошибка сервера                               |

При статусах `OK`, `NOT_FOUND` и `NOT_SET` payload имеет формат, описанный для соответствующей команды.

Для остальных статусов payload содержит поле `message: string` с описанием ошибки. Оно предназначено для вывода пользователю и не должно использоваться клиентом для определения типа ошибки — для этого предусмотрено поле `status`.

Максимальная длина сообщения об ошибке — 256 байт.

## 7. Обработка некорректных пакетов

Сервер обрабатывает ошибки в зависимости от того, на каком этапе они обнаружены.

| Ошибка                                                        | Действие сервера                   |
| ------------------------------------------------------------- | ---------------------------------- |
| Датаграмма короче заголовка или превышает максимальный размер | Пакет отбрасывается без ответа     |
| Неверный `magic`                                              | Пакет отбрасывается без ответа     |
| `payload_len` не совпадает с размером payload                 | Пакет отбрасывается без ответа     |
| Неподдерживаемая версия                                       | Возвращается `UNSUPPORTED_VERSION` |
| Неизвестный `opcode`                                          | Возвращается `UNKNOWN_OPCODE`      |
| Некорректный формат payload                                   | Возвращается `BAD_REQUEST`         |
| Ключ, значение или паттерн превышает лимит                    | Возвращается `TOO_LARGE`           |

Во всех ответах `request_id` должен совпадать с идентификатором исходного запроса. Размер ответа вместе с заголовком не может превышать 1400 байт.

## 8. Примеры пакетов

Ниже приведены примеры запросов и ответов в шестнадцатеричном виде. Каждый пакет начинается с 16-байтового заголовка.

### GET: запрос значения `user:1`

`request_id = 1`.

```
4B 56 01 02 00 00 00 08   magic, version=1, opcode=GET, status=0, flags=0, payload_len=8
00 00 00 00 00 00 00 01   request_id = 1
00 06 75 73 65 72 3A 31   key = "user:1"
```

### GET: успешный ответ

Сервер вернул значение `Alice`.

```
4B 56 01 02 00 01 00 07   status=OK, flags=ответ, payload_len=7
00 00 00 00 00 00 00 01   request_id = 1
00 05 41 6C 69 63 65      value = "Alice"
```

### GET: ключ не найден

```
4B 56 01 02 01 01 00 00   status=NOT_FOUND, flags=ответ, payload_len=0
00 00 00 00 00 00 00 01   request_id = 1
```

### SET: запись значения `hi` по ключу `k`

TTL составляет 5000 мс, `request_id = 2`.

```
4B 56 01 03 00 00 00 0F   opcode=SET, payload_len=15
00 00 00 00 00 00 00 02   request_id = 2
00 01 6B                  key = "k"
00 02 68 69               value = "hi"
00 00 00 00 00 00 13 88   ttl_ms = 5000
```

### KEYS: поиск ключей по паттерну `user:.*`

Это первый запрос, поэтому `cursor = 0`. Значение `limit = 0` означает, что сервер использует лимит по умолчанию. Идентификатор запроса — `3`.

```
4B 56 01 08 00 00 00 13   opcode=KEYS, payload_len=19
00 00 00 00 00 00 00 03   request_id = 3
00 07 75 73 65 72 3A 2E 2A   pattern = "user:.*"
00 00 00 00 00 00 00 00   cursor = 0
00 00                     limit = 0
```
