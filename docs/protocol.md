# Бинарный протокол

Протокол описывает обмен данными между клиентом и сервером по UDP. Одна датаграмма содержит одно сообщение - запрос или ответ.

## 1. Общие правила

Все многобайтные числа передаются в формате big-endian.

В протоколе используются следующие типы:

- `u8`, `u16`, `u64` - беззнаковые целые числа;
- `i64` - знаковое целое число;
- `bytes` - длина данных (`u16`), затем сами данные;
- `string` - строка в UTF-8, передаваемая так же, как `bytes`.

При чтении каждого поля нужно проверять, что в буфере достаточно данных. Если поле обрезано или выходит за границы буфера, декодер возвращает ошибку. Паниковать при этом нельзя.

## 2. Ограничения

| Параметр | Значение |
|---|---:|
| `MaxPacketSize` - максимальный размер пакета | 1400 байт |
| `HeaderSize` - размер заголовка | 16 байт |
| `MaxPayloadSize` - максимальный размер payload | 1384 байта |
| `MaxKeyLen` - максимальная длина ключа | 256 байт |
| `MaxValueLen` - максимальная длина значения | 1024 байта |
| `MaxPatternLen` - максимальная длина regex | 256 байт |
| `MaxErrorLen` - максимальная длина сообщения об ошибке | 256 байт |
| `MaxTTLMs` - максимальный TTL | 9223372036854 мс |

Максимальный payload для `SET` с ключом длиной 256 байт, значением длиной 1024 байта и полем TTL занимает 1292 байта. Это меньше установленного лимита в 1384 байта.

`MaxTTLMs` ограничивает TTL значением, которое можно безопасно перевести в наносекунды и сохранить в `int64`. Если клиент передаёт большее значение, сервер отвечает `INVALID_ARGUMENT`.

## 3. Заголовок пакета

Заголовок занимает 16 байт. Его формат одинаков для запросов и ответов.

| Смещение | Размер | Поле | Описание |
|---|---:|---|---|
| 0 | 2 | `magic` | Константа `0x4B56` |
| 2 | 1 | `version` | Версия протокола (`0x01`) |
| 3 | 1 | `opcode` | Код команды |
| 4 | 1 | `status` | Код результата |
| 5 | 1 | `flags` | Признак запроса или ответа |
| 6 | 2 | `payload_len` | Размер payload в байтах |
| 8 | 8 | `request_id` | Идентификатор запроса |

Поле `magic` всегда равно `0x4B56`, а `version` - `0x01`.

В `flags` используется только младший бит (`0x01`): `0` означает запрос, `1` - ответ. Все остальные биты должны быть нулевыми.

В запросах `status` всегда равен `0x00`. Сервер копирует `request_id` из запроса в ответ, чтобы клиент мог сопоставить их между собой.

После заголовка идёт payload размером `payload_len` байт.

### Проверка заголовка

Перед обработкой команды сервер проверяет:

1. Размер датаграммы - от 16 до 1400 байт.
2. Значение `magic` - должно быть `0x4B56`.
3. Версию протокола.
4. Совпадение `payload_len` с фактическим размером payload.
5. Отсутствие неизвестных битов в `flags`.
6. Для запроса - `flags = 0` и `status = 0`. Для ответа младший бит `flags` должен быть равен `1`.

Если формат payload не соответствует команде или после разбора остаются лишние байты, запрос считается некорректным.

## 4. Команды

| Код | Команда | Назначение |
|---|---|---|
| `0x01` | `PING` | Проверка связи |
| `0x02` | `GET` | Получение значения |
| `0x03` | `SET` | Запись значения |
| `0x04` | `SETNX` | Запись, если ключ ещё не существует |
| `0x05` | `DEL` | Удаление ключа |
| `0x06` | `TTL` | Получение оставшегося времени жизни |
| `0x07` | `EXPIRE` | Установка времени жизни |
| `0x08` | `KEYS` | Поиск ключей по регулярному выражению |

В ответе сохраняются `opcode` и `request_id` исходного запроса. Для неизвестной команды сервер возвращает `UNKNOWN_OPCODE`.

Во всех командах просроченный ключ считается отсутствующим.

## 5. Формат команд

### PING

У запроса и успешного ответа payload пустой. Команда нужна, чтобы проверить, доступен ли сервер.

### GET

| Сообщение | Payload |
|---|---|
| Запрос | `key: bytes` |
| Ответ `OK` | `value: bytes` |
| Ответ `NOT_FOUND` | Пустой |

Если ключ найден, сервер возвращает его значение. Если ключ отсутствует или истёк, возвращается `NOT_FOUND`.

### SET

| Сообщение | Payload |
|---|---|
| Запрос | `key: bytes`, `value: bytes`, `ttl_ms: u64` |
| Ответ `OK` | Пустой |

Команда записывает значение по указанному ключу. Если ключ уже существует, его значение и TTL заменяются новыми.

`ttl_ms` задаёт время жизни ключа в миллисекундах:

- `0` - ключ хранится без ограничения по времени;
- от `1` до `MaxTTLMs` - ключ удаляется после истечения указанного времени;
- больше `MaxTTLMs` - сервер возвращает `INVALID_ARGUMENT`.

### SETNX

Формат запроса такой же, как у `SET`.

| Статус | Результат |
|---|---|
| `OK` | Ключ создан, payload пустой |
| `NOT_SET` | Ключ уже существует, payload пустой |

В отличие от `SET`, команда не перезаписывает существующий ключ. Если ключ уже истёк, он считается отсутствующим и запись выполняется. Правила для TTL такие же, как у `SET`.

### DEL

| Сообщение | Payload |
|---|---|
| Запрос | `key: bytes` |
| Ответ `OK` | Пустой |
| Ответ `NOT_FOUND` | Пустой |

`OK` означает, что ключ удалён. Если ключ отсутствует или уже истёк, сервер возвращает `NOT_FOUND`.

### TTL

| Сообщение | Payload |
|---|---|
| Запрос | `key: bytes` |
| Ответ `OK` | `ttl_ms: i64` |
| Ответ `NOT_FOUND` | Пустой |

Ответ содержит оставшееся время жизни ключа в миллисекундах, округлённое вниз.

- `-1` - у ключа нет TTL;
- `0` - до истечения осталось меньше одной миллисекунды;
- положительное число - оставшееся время жизни.

Других отрицательных значений нет. Если ключ отсутствует или уже истёк, сервер возвращает `NOT_FOUND`.

### EXPIRE

| Сообщение | Payload |
|---|---|
| Запрос | `key: bytes`, `ttl_ms: u64` |
| Ответ `OK` | Пустой |
| Ответ `NOT_FOUND` | Пустой |

Команда задаёт новый TTL существующему ключу, отсчитывая время от момента выполнения команды. Если TTL уже был установлен, он заменяется. Значение ключа не меняется.

TTL должен быть больше нуля и не превышать `MaxTTLMs`. В противном случае сервер возвращает `INVALID_ARGUMENT`.

Если ключ отсутствует или уже истёк, возвращается `NOT_FOUND`.

### KEYS

| Сообщение | Payload |
|---|---|
| Запрос | `pattern: bytes`, `cursor: u64`, `limit: u16` |
| Ответ `OK` | `next_cursor: u64`, `count: u16`, затем `count` ключей типа `bytes` |

Команда возвращает ключи, подходящие под регулярное выражение RE2. Просроченные ключи в результат не попадают.

Поиск выполняется по любой части ключа. Для совпадения со всем ключом используй `^` и `$`. Пустой паттерн подходит всем ключам.

Результат может не поместиться в один пакет, поэтому ключи возвращаются частями:

- Для первого запроса передаётся `cursor = 0`.
- Если остались ещё ключи, сервер возвращает ненулевой `next_cursor`.
- Для получения следующей части клиент передаёт этот курсор в новом запросе.
- Когда ключи закончились, `next_cursor = 0`.

Если совпадений нет, сервер возвращает `OK`, `count = 0` и `next_cursor = 0`.

Ключи возвращаются в лексикографическом порядке. При этом каждый запрос заново формирует список подходящих ключей. Если ключи изменились между запросами, некоторые из них могут встретиться повторно или быть пропущены. Обход не гарантирует согласованный снимок данных.

Курсор является внутренним значением сервера. Клиент должен только передавать его в следующем запросе, не пытаясь вычислять или изменять самостоятельно.

`limit` задаёт максимальное количество ключей в ответе. При `limit = 0` используется значение по умолчанию. Если выбранные ключи не помещаются в пакет, сервер уменьшает размер порции.

Если регулярное выражение некорректно, сервер возвращает `INVALID_ARGUMENT`.

## 6. Статусы ответов

| Код | Статус | Когда используется |
|---|---|---|
| `0x00` | `OK` | Команда выполнена успешно |
| `0x01` | `NOT_FOUND` | Ключ отсутствует или истёк |
| `0x02` | `NOT_SET` | `SETNX` не выполнен, потому что ключ уже существует |
| `0x10` | `BAD_REQUEST` | Некорректный payload |
| `0x11` | `UNKNOWN_OPCODE` | Неизвестная команда |
| `0x12` | `UNSUPPORTED_VERSION` | Неподдерживаемая версия протокола |
| `0x13` | `TOO_LARGE` | Ключ, значение или паттерн превышает лимит |
| `0x14` | `INVALID_ARGUMENT` | Некорректный аргумент, в том числе недопустимый TTL или regex |
| `0x7F` | `INTERNAL_ERROR` | Внутренняя ошибка сервера |

Для `OK`, `NOT_FOUND` и `NOT_SET` формат payload определяется соответствующей командой.

Для остальных статусов payload содержит `message: string` - текстовое описание ошибки. Клиент может показать его пользователю, но не должен определять тип ошибки по тексту. Для этого используется `status`.

Длина сообщения об ошибке не должна превышать 256 байт.

## 7. Обработка некорректных пакетов

| Ситуация | Действие |
|---|---|
| Датаграмма короче заголовка или больше 1400 байт | Отбросить пакет без ответа |
| Неверный `magic` | Отбросить пакет без ответа |
| `payload_len` не совпадает с размером payload | Отбросить пакет без ответа |
| Неподдерживаемая версия | Ответить `UNSUPPORTED_VERSION` |
| Неизвестный `opcode` | Ответить `UNKNOWN_OPCODE` |
| Payload не соответствует формату команды | Ответить `BAD_REQUEST` |
| Ключ, значение или паттерн превышает лимит | Ответить `TOO_LARGE` |

Во всех сформированных ответах `request_id` должен совпадать с идентификатором запроса. Полный размер ответа, включая заголовок, не должен превышать 1400 байт.

## 8. Примеры пакетов

Все примеры приведены в шестнадцатеричном виде. Первые 16 байт каждого пакета - заголовок.

### GET: запрос ключа `user:1`

`request_id = 1`.

```text
4B 56 01 02 00 00 00 08   magic, version=1, opcode=GET, status=0, flags=0, payload_len=8
00 00 00 00 00 00 00 01   request_id = 1
00 06 75 73 65 72 3A 31   key = "user:1"
```

### GET: успешный ответ

Сервер вернул значение `Alice`.

```text
4B 56 01 02 00 01 00 07   status=OK, flags=ответ, payload_len=7
00 00 00 00 00 00 00 01   request_id = 1
00 05 41 6C 69 63 65      value = "Alice"
```

### GET: ключ не найден

```text
4B 56 01 02 01 01 00 00   status=NOT_FOUND, flags=ответ, payload_len=0
00 00 00 00 00 00 00 01   request_id = 1
```

### SET: запись значения `hi` по ключу `k`

TTL - 5000 мс, `request_id = 2`.

```text
4B 56 01 03 00 00 00 0F   opcode=SET, payload_len=15
00 00 00 00 00 00 00 02   request_id = 2
00 01 6B                  key = "k"
00 02 68 69               value = "hi"
00 00 00 00 00 00 13 88   ttl_ms = 5000
```

### KEYS: поиск по паттерну `user:.*`

Это первый запрос, поэтому `cursor = 0`. Значение `limit = 0` означает, что сервер использует лимит по умолчанию. `request_id = 3`.

```text
4B 56 01 08 00 00 00 13   opcode=KEYS, payload_len=19
00 00 00 00 00 00 00 03   request_id = 3
00 07 75 73 65 72 3A 2E 2A   pattern = "user:.*"
00 00 00 00 00 00 00 00   cursor = 0
00 00                     limit = 0
```
